# SPEC-FW-015 — Pip Legacy Retirement

## Status

Proposed

## Context

[ADR-FW-002](ADR-FW-002.md) standardized the framework on `uv` as the sole
package manager for *new* functionality and marked `pip`/`requirements*.txt`
as legacy. [SPEC-FW-IMPL-PLAN.md](SPEC-FW-IMPL-PLAN.md) Phase 0 implemented the
"legacy-mark, do not remove" recommendation: `ai/installer.py`,
`scripts/hooks/sync_dependencies.py`, and `scripts/run_pip_init.py` all carry
comments stating that `pip` is legacy per ADR-FW-002 and will not gain new
functionality.

Phases 1-5 of the impl plan (SPEC-FW-006 through SPEC-FW-011) are now
implemented: the typed capability registry, the shared profile parser, the
restore command, the multi-stack scanner/`llms.txt` pipeline, and the SaaS
capability expansion all assume `uv` + `pyproject.toml`/`uv.lock` as the
dependency source of truth. The `pip` axis has received **no new
capabilities** during this program, confirming ADR-FW-002's premise — but it
is still fully wired into the installer's public API, the sync hook, the
package bundler, and the test suite.

This spec defines the **next phase**: actually retiring the `pip` code paths,
as anticipated by Open Decision #2 in `SPEC-FW-IMPL-PLAN.md` ("if the team
wants full removal of `scripts/run_pip_init.py`/`requirements.*.txt`/the
`package_manager` axis, that should be its own ADR with its own migration
plan, separate from this program").

## Decision

Retire `pip` as a supported package manager for **new and existing hosts**
generated by this framework, completing ADR-FW-002. `uv` +
`pyproject.toml`/`uv.lock` becomes the **only** dependency management path the
installer, sync hook, and bundler support.

This is a **breaking change** for any host still using the retired profile
format — see Migration Strategy.

---

## Contract

### `ai/installer.py`

- Remove `PACKAGE_MANAGERS`, `prompt_package_manager`, `validate_package_manager`.
- Remove `LOCAL_REQUIREMENTS_PATH`, `CLOUD_REQUIREMENTS_PATH`, `DEV_REQUIREMENTS_PATH`,
  `should_copy_requirements_file`.
- Collapse `should_copy_package_file` to always select the `uv` branch
  (retired profile format, `pyproject.toml`, `uv.lock` copied; any
  `requirements*.txt` in the template root excluded unconditionally).
- `install_template(...)` drops the `package_manager` parameter entirely
  (no default, no validation) — installs are uv-only.
- `render_target_file` / `copy_template_file` drop the `package_manager`
  parameter and the pip branches for `.pre-commit-config.yaml`, `Makefile`,
  and retired profile format — only the `uv` rendering remains.
- The retired profile format is neither written nor read.

### `scripts/hooks/sync_dependencies.py`

- Remove `PACKAGE_MANAGERS`, the `--manager` CLI argument, `requirement_files`,
  `REQUIREMENTS_GLOB`, and the pip branches of `dependency_files` and
  `install_command`.
- `dependency_files`/`install_command` always resolve the `uv` path
  (`pyproject.toml`, `uv.lock`, retired profile format; `uv sync ...`).
- `resolve_profile` no longer special-cases `manager == "uv"` — there is only
  one manager.

### `scripts/run_pip_init.py`

- Delete the file. The `Makefile`'s `init` target template becomes the `uv`
  variant unconditionally (`$(BOOTSTRAP_PYTHON) scripts/run_uv_sync.py init`).

### `install_linux.py` / `install_windows.py`

- Remove `--package-manager`, `--pip`, `--uv` flags and the associated
  mutual-exclusion validation. Installs are always uv-based; no manager prompt
  or flag is offered.

### `scripts/package.py`

- Remove `detect_package_manager`, `CLOUD_REQUIREMENTS`, and the
  `--package-manager` flag. `runtime_requirements_text` always uses
  `uv export --no-dev --extra cloud --format requirements.txt`.

### `ai/tools/inspect_project.py`

- Remove `requirements*.txt` from `_detect_languages`'s Python-detection
  predicate and from `_detect_data_stack`/`_detect_cloud`'s file-content scan
  allow-lists — `pyproject.toml` (and `.py` files) are sufficient signals.

### Capability descriptors

- [ai/capabilities/business/saas.yaml](../../ai/capabilities/business/saas.yaml):
  remove the `requirements.saas.txt` path entry.

### Repo-root requirements files

- Delete `requirements.local.txt`, `requirements.cloud.txt`,
  `requirements.dev.txt`, `requirements.saas.txt` from the template repository.
  `pyproject.toml` + `uv.lock` (with the `local`/`cloud`/`saas`/`supabase`
  extras and `dev-local`/`dev-cloud` groups) are already the authoritative,
  equivalent source — verified during Phase 1 (SPEC-FW-006/008) and exercised
  by every `uv sync` invocation since.

### `Makefile`

- `init` target becomes `$(BOOTSTRAP_PYTHON) scripts/run_uv_sync.py init`
  unconditionally (matches what the installer already renders for uv hosts
  today — this just makes it the template's own default too).

### Tests

- [tests/test_installer.py](../../tests/test_installer.py): remove
  `test_local_install_copies_only_local_and_dev_requirements`,
  `test_cloud_install_copies_cloud_requirements`'s pip-specific assertions
  (keep a uv-equivalent if not already covered by
  `test_uv_install_*`-style cases), `test_existing_host_requirements_txt_is_left_untouched`
  (or rewrite for a generic untouched-file case unrelated to pip),
  `test_install_skips_saas_capability_by_default` /
  `test_install_includes_saas_capability_when_selected` to drop
  `requirements.saas.txt` assertions and `package_manager="pip"` args, and the
  `--pip` CLI smoke test.
- [tests/test_script_wrappers.py](../../tests/test_script_wrappers.py): remove
  `test_pip_init_wrapper_dry_run`.
- [tests/test_sync_dependencies.py](../../tests/test_sync_dependencies.py):
  remove `test_pip_main_installs_profile_requirements` and any other
  `--manager pip` cases; keep/extend uv-path coverage.
- [tests/test_restore_project.py](../../tests/test_restore_project.py): remove
  the `requirements.saas.txt` fixture entry and the
  `package_manager=pip\n...` retired profile format fixture (or repoint it at a
  uv-only fixture).

### Docs

- [README.md](../../README.md), [docs/linux_setup/README.md](../../docs/linux_setup/README.md),
  [docs/windows_setup/README.md](../../docs/windows_setup/README.md): remove

## Compatibility Strategy

There is no runtime compatibility layer for the retired profile format.
`ai/runtime/profile.py`, restore, sync, hooks, and installers accept only
`.template-profile.yaml`. Migration is explicit and happens before invoking
current tooling.

- The removed format is not inspected for package-manager metadata.




- Restore and sync fail validation when `.template-profile.yaml` is absent.





- No automatic `requirements.txt` → `pyproject.toml` migration tool is in
  scope for this spec (see Out of Scope).

---

## Migration Strategy

### For existing hosts using the retired profile format

1. Manually create `pyproject.toml` (or run `uv init` and re-add dependencies
   from `requirements*.txt` via `uv add`).
2. Run `uv lock` to generate `uv.lock`.
3. Create `.template-profile.yaml` with the current schema, environment,
   capabilities, and dependency policy. Remove the retired profile file.
4. Update the host's `sync-dependencies` hook invocation to drop `--manager
   pip` (the flag will be removed; passing it after this spec lands is an
   error).
5. Update the `Makefile`'s `init` target to
   `$(BOOTSTRAP_PYTHON) scripts/run_uv_sync.py init`.
6. Delete `requirements*.txt` from the host once `uv sync` is verified working.
7. Re-run `python scripts/restore_project.py --dry-run --pretty` to confirm
   the consistency invariant holds against the new profile.

### For the template repository itself

Already on `uv` (`pyproject.toml` + `uv.lock` are authoritative since before
Phase 1). This spec only removes the now-unused `requirements.*.txt` files and
the code paths that reference them.

## Invariants

- After this spec, `git grep -i "package_manager"` and `git grep -i "PACKAGE_MANAGERS"`
  return zero matches in `ai/`, `scripts/`, `install_linux.py`,
  `install_windows.py`.
- `git ls-files | grep -i requirements` returns zero matches (no
  `requirements*.txt` tracked in the template repo, no `run_pip_init.py`).
- `python scripts/restore_project.py --dry-run --pretty` continues to report
  zero `missing` entries in `ai/skills.yaml` consistency checks (removing
  `requirements.saas.txt` from `ai/capabilities/business/saas.yaml` does not
  orphan any skill — it is a dependency file, not a skill path).
- All tests pass (`pytest -q`); `ruff check .` and `ruff format --check .`
  remain clean for touched files.
- A fresh `python install_windows.py --target <tmp> --local --dry-run` (no
  package-manager flag) produces a file set identical to today's
  `--local --uv --dry-run` output (uv becomes the unconditional default, not a
  new behavior).

## Risk Assessment

| Aspect | Rating | Notes |
|---|---|---|
| Risk level | Medium | Touches `ai/installer.py` (core, but only the pip branches — already isolated by Phase 0's legacy markers), sync hook, two CLI entrypoints, bundler, and ~6 test files. No new architecture. |
| Breaking-change potential | **Medium, scoped** | Breaking *only* for hosts with `package_manager=pip`. Per ADR-FW-002 context, **no active framework project** uses this path (ETL/FastAPI/SaaS/AI/infra projects all use uv) — but any such host must follow the Migration Strategy above. |
| Implementation effort | M | Mechanical removal across ~8 files; the careful part is the `should_copy_package_file`/`render_target_file` collapse in `ai/installer.py` and updating the ~10 affected tests. |
| Testing effort | S | Mostly deletions of pip-specific test cases; a handful of existing uv-path tests already provide equivalent coverage. |
| Migration effort | S (template repo) / M (external pip hosts, if any exist) | Template repo: delete 4 files + update descriptor. External hosts: manual `uv init`/`uv add`/`uv lock` per Migration Strategy. |

---

## Out of Scope

- An automated `requirements.txt` → `pyproject.toml` conversion tool —
  migration is manual per the steps above.
- Any change to `uv`-path behavior or capability resolution beyond removing
  compatibility with the retired profile format.
- Re-litigating SPEC-FW-006 through SPEC-FW-011 (already implemented).
- Renaming or restructuring `ai/capabilities/business/saas.yaml` beyond
  removing the single `requirements.saas.txt` path entry.
